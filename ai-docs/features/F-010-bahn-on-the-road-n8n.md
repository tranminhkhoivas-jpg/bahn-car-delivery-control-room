## Track scope
Bahn only. This is part 2 of the Bahn brief, "one real agent for one area", for the "On the road" area. The control-room site (part 1) is [[F-012-bahn-control-room-site]]; it reads this feature's tables and calls its webhooks.

## Purpose (why this exists, tied to project goal)
A real agent setup for the whole on-the-road area: a router sends each event to the problem workflow(s) that own it, and each workflow does the cheap work itself (reads the order, asks the driver, checks timing, searches ferries, trains and flights, ranks options). A person gets ONE plan per order to approve, with every cost line and the customer draft in it. Nothing is booked, changed or sent to a customer without a person. This follows the Bahn rules in [[F-004-bahn-entry]].

## Behavior (what the user/visitor/admin sees and can do; edge cases and error states)
**Ways in (all reach the router):**
- System event: `POST http://127.0.0.1:5678/webhook/bahn/on-the-road` with `{order_ref, source, event, simulate?}`. It answers at once with `{"message":"Workflow was started"}` and works in the background (2-5 min); the control room polls.
- Operator chat: `http://127.0.0.1:5678/webhook/8e3f2b6a-6c4d-4f7a-b1e2-3c9d8a7f6e21/chat` (the `CD-######` reference is picked out of the message).
- Wake-up (`source: follow_up`) from the act and plan-step workflows, see "Waiting on the buyer".

**Routing (code + GLiDE, no LLM agent):**
- Dataset alert codes in the event text map to workflows: VEHICLE_WARNING / SAFETY_STOP to vehicle; FERRY_SOLD_OUT / FERRY_CONNECTION_RISK / TRAVEL_CAPACITY / POSITIONING_AT_RISK / DELIVERY_PROMISE_UNACHIEVABLE to journey; TRACKING_GAP / FERRY_TRACKING_GAP_CONTEXT to tracking; DELIVERY_ACCESS_RISK / SITE_ACCESS_CONFLICT to destination; RELEASE_DOCUMENT_UNCLEAR to documents.
- One GLiDE call asks 8 yes/no questions about the free text (7 categories plus `driver_cannot_continue`), threshold 0.5. DRIVER_AVAILABILITY_RISK goes to incident when the driver cannot continue, otherwise to journey.
- Root cause wins: if vehicle, documents, destination or incident is chosen, journey is dropped (those workflows call journey themselves). Tracking runs alongside. Order: incident, vehicle, documents, destination, journey, tracking, expenses. Nothing matched goes to general.
- A follow-up, chat or event with no new category reuses the workflows from the case's last `route` line (for example "Plan #12 was rejected: re-plan" goes back to incident); only a case with no open workflow goes to general.
- The router logs one `route` timeline line, e.g. "Routed to: vehicle, tracking. codes: ...; GLiDE: vehicle 1.00, journey 0.76, tracking 0.99; journey dropped ...". `simulate: driver_unreachable` also logs a `test_flag` line.
- No double requests: each workflow run uses memory session `case-<order_ref>-<workflow>-<closes>`, so a repeat event for an open case joins the same conversation; a new session starts only after the case was closed.

**The 8 problem workflows (one LLM agent each, same template):** vehicle, journey, destination, tracking, incident, documents, expenses, general. Each has its own playbook plus shared hard rules:
- Safety first: the first driver message asks if they are safe. Danger or illness: tell them to call 112 and call `escalate_urgent`. On a new incident event the router itself sends the driver the 112 safety line (once per open case) before any workflow starts (node chain: Resume, Safety line?, 112 line, Route rows), so the agent's first question always comes after it. Live-checked 2026-10-25 on CD-420322 (deer strike): 112 line was timeline #234, the agent's first question #236. In that run the agent then asked "are you safe" although the simulated driver had just said so in reply to the 112 line. Repo agent instructions (`agents/_shared.md` rule 3, `incident.md` step 1, `vehicle.md` step 1) now say to read the conversation first and not re-ask when the driver already answered. Promoted to production 2026-10-25 with the user's approval (journey v3, the other 7 v2; the replaced v1 versions were plain repo text). Live re-test on CD-420710 still re-asked: the agent read the conversation when it started, and the driver's reply to the 112 line was stored 0.07 s before the agent's own question went out, so the rule had nothing to see. Accepted as is for the demo (user decision 2026-10-25): the driver may get the safety question twice. The rejected alternative was to treat the 112 line as the safety question so agents skip their own.
- No mechanical advice, never says a car may be driven, never contacts customers (only `driver` and `pickup_site`).
- No driver reply: ask once more, then `escalate_urgent` with the last known location.
- Vehicle (stages safety, facts_photo, solution_question, staff_check, buyer_revise, journey_options, plan): the buyer is asked how to solve it; an employee task (`ask_time: ready`) asks staff to approve the buyer's choice and give the car-ready time; a staff note becomes a revised buyer draft that staff approve before it is sent; the timing options run only after staff agree and a ready time exists.
- Incident (stages safety, employee_task, replacement, handover, journey_options, plan): replacement driver plus the sick driver's trip home through `plan_driver_travel`; a handover task (`ask_time: handover`) asks when the driver can start driving, with or without a known time.
- **Asked times** (`create_employee_task` input `ask_time` = `ready` or `handover`): the control room shows a date-time field; empty means "not known yet". `/webhook/bahn/step` takes `time` (ISO). A ready time gets the safety margin `repair_slack_min` (60 min) and the note says "Car ready at X (plan from X+margin)". The step note tag becomes `[ask_time <kind> at <ISO>]` or `[ask_time <kind> unknown]`; a time that is not a date-time is refused.
  - Time not known: otr_reminders opens a check-in wait `checkin:<order>` for staff. Every `handover_checkin_min` (30 min) it asks staff again (new task, only if none is open) and wakes the agent for a check: check_journey (tracking moving = arrived) and the ferry search only to warn about a sailing near sell-out; the buyer is never asked. The check-in stops when a time is given or the driver writes.
  - Handover time known: a driver wait `arrival:<step id>` asks the driver to confirm arrival when the demo clock reaches that time.
- Vehicle, destination, tracking, incident and documents have a `journey_disruption` tool that runs the journey workflow in draft mode and returns checked plan lines to merge into their one plan.
- Every reply uses the four parts **Order**, **What I did**, **Needs your decision**, **Evidence**; times in UTC.

**Code tools (no LLM; every number comes from code):**
- `check_journey`: is the tracking gap normal (ferry leg in progress, hotel stay or planned rest, before the pickup slot, or 45 min or less), last known position (straight line pickup to delivery at the tracked progress, snapped to the nearest of 37 dataset cities), and a road arrival check: km left at 75 km/h, 45 min break per 4.5 h, 11 h rest after 9 h driving per day; when the last tracking row carries a later driver-app `estimated_delivery_at`, that later ETA is used (not for a given restart time). Verdict `on_time` (at least 3 h before the window end), `at_risk` or `late`; when late it suggests a new window inside site hours.
- `plan_driver_travel`: purpose `replacement_to_vehicle` or `driver_return`. Replacement: picks free drivers (active, not on an ASSIGNED or IN_PROGRESS assignment, not the current driver) nearest the handover city, then their travel. Return: to the driver's home city. Options are the dataset TRAIN/FLIGHT quotes on that city pair plus `mock_generated` options (trains on one landmass under 900 km, flights over 400 km; about 15% sold out; same input gives the same output), ranked by earliest arrival, then cost.
- `plan_rebooking`: ferry search and scoring (see Decisions). A sailing reported sold out (timeline event, Telegram or driver text since the last close matching "sold out / fully booked / no space / slot unavailable", or an unresolved `FERRY_SOLD_OUT` alert) is marked SOLD_OUT "per alert or report" and not offered; an already booked sailing (from done `book_ferry` steps) counts as failed.
- `propose_plan`: one plan with mixed lines: book_ferry, book_hotel, book_train, book_flight, book_recovery, approve_cost, change_delivery_window, reassign_driver, notify_driver, customer_message, buyer_decision, staff_task. Each line has `cost_cents` in EUR; the total is computed. An approve_cost line for a dataset expense converts its currency (DKK at 7.46 per EUR; any other non-EUR currency is refused). Ferry, train and flight lines must match a fresh search. A date change or a late ferry needs a buyer draft and a buyer_decision line; a buyer_decision line without a buyer draft in the same plan is refused (nobody would be asked). Only one pending plan per order. In draft mode it returns the checked lines instead of filing. Lines run in the order bookings first, people last, except a check before booking: a staff_task line with `before_booking: true` (for example "cancel the old booking first") is put first, opens as a waiting step (`ref: before_booking`, step 0) the moment the plan is filed, and the Act workflow refuses to approve or offer the plan until a person marks it done ("Do the check first (step #N) ..."). Marking it done does not wake the agent; the case reads "check before booking done. The plan can now be approved." Marking it "Could not do it" wakes the agent to re-plan. The done check is not opened again when the plan is booked.
- `escalate_urgent`: case status `urgent`, an `escalation` timeline line with the last known location, and a `staff_task` step with `proposal_id: escalation` that a person sees at once (no approval).

**Re-plans and the coordinator:** GLiDE resume gets every event since the last close (`events_since_close`, last 15) besides the newest one. When two or more workflows run and one of them still has plan lines waiting for a decision, GLiDE may answer `keep_plan` for it: that workflow is not run again and the coordinator reuses its waiting lines (if every workflow would keep, the first one runs anyway).

**Fact check on drafted messages:** after the writer, code checks that every HH:MM time and EUR amount in the buyer, delivery-contact and driver texts appears in the plan facts, and GLiDE (`noul` question "grounded", threshold `glide_grounding` 0.05) checks every time, date, price, place and promise. GLiDE gets only the facts (from "PLAN (checked by code)") and the three messages as one text. A miss does not block: the plan's rationale gets "Fact check warning - check the messages: ..." for the employee. Times written inside timestamps in the facts (`2026-10-22T10:00Z`) count as facts. Live run 2026-10-25 on CD-420603 (ferry sold out): plan #10 filed with the warning, driver got the status note. Calibration 2026-10-25 on the drafts of runs 3304 and 3453: drafts that matched the facts scored 0.10-0.19, the same drafts with one wrong price or place 0.003-0.016 (question wording made no difference), so the threshold was lowered from 0.5 to 0.05 (default and live value). Two orders only; recheck with the Promptfoo suite. Live run 3453 (a Telegram message linked by staff in the control room) filed plan #11 with the buyer's question merged, replacing the expired #10.

**Driver status (P7):** when a plan is filed, the driver gets "Bahn is deciding on a change for this delivery. Keep to your current plan until we confirm." (Telegram kind `driver_status`, no wait, no simulated reply). On an offer the driver gets "keep to your current plan" again; the real instruction comes only after approval (and the buyer's choice).

**Staff to driver:** `POST /webhook/bahn/message-driver` with `{order_ref, text, operator}` sends a staff message to the driver (no approval; drivers may be messaged). The operator name is required; the timeline actor is `staff (<name>)`; the driver's reply wakes the agent like any driver message.

**Retries:** every GLiDE, OpenRouter, LLM chain and agent node retries up to 3 times, 2 s apart.

**Approve and execute:** `POST /webhook/bahn/act` with `{proposal_id, decision, operator, note?, option?, send?, confirm_unclear?, simulate?}`. Decisions: `approve` and `reject` on a `pending` plan; `buyer_accept` and `buyer_decline` on an `offered` plan.
- **One decision at a time:** before anything runs, the plan is claimed (status set to `deciding` only where it still has the needed status). A second click or a second person gets "is being decided by someone else or was already decided"; a refused decision puts the old status back. Live-tested 2026-10-25: two simultaneous approvals of proposal #9 ran once.
- **Approve, buyer needed** (the plan changes the date or asks the buyer something, or the employee sent `send: ask_buyer`): status `offered`. The buyer draft is sent on Telegram with one button per option (F-015), the driver gets "keep to your current plan" (status update, not a new instruction), and a `buyer_decision` step waits until the offer deadline (the plan's `valid_until`, else now + `offer_valid_min`, shown in the buyer's local time). Nothing is booked; the delivery-contact draft is held.
- **Approve, book now** (on-time plan, default `send`): the chosen option (`option` letter, else the recommended one) plus the common lines are booked.
- **buyer_accept** (`option` = the buyer's letter, `note` = their words): an answer after the deadline gives `expired` and wakes the agent for a revised offer. Otherwise a final check right before booking (ferry against a fresh ferry search, train/flight against a fresh travel search, price and availability, and a sailing promised on time must still arrive on time: "the sailing no longer arrives on time (now X h late)"); a change gives `failed`, nothing booked, and the agent re-plans and asks the buyer again. Then the bookings, the delivery-contact message and the driver instruction, which names the chosen option, what was booked and the booking refs (propose_plan's placeholder "the option the buyer chooses" is replaced). The waiting buyer step is closed and reads "Buyer chose option X". The coordinator writes the buyer draft before any deadline exists; its prompt says the deadline is not set yet and not to mention one, because the send step adds the "Please choose by" line. An answer to a question-only plan always wakes the agent with the answer.
- **buyer_decline / reject:** nothing booked (`declined` / `rejected`); the agent is woken with the reason and must make a plan that avoids it. Reject needs a note. The wake names exactly the workflows that made the plan (taken from the plan's rationale prefixes).
- **Unclear notes:** a reject reason, and an answer to an employee task on `/step`, go through `BAHN tool · check_note` (GLiDE clarity question, threshold `glide_note_clarity`). Unclear returns `{ok:false, unclear:true, question}` with a Claude Haiku 5.5 follow-up question and changes nothing; `confirm_unclear: true` keeps the note as written. If GLiDE is down the note passes unchecked.
- Bookings: provider timeouts retry up to `booking_retries`; a failed ferry, train or flight stops the plan (`failed`, rest skipped); a failed hotel gives `partly_executed`. Any failed booking or failed final check wakes the agent on its own; it re-plans only the broken part and files one new plan that waits for a person. A failed booking step stops blocking the case once a later plan booked the same kind.
- In an executed plan: buyer and delivery-contact messages and the driver instruction are sent on Telegram (approved with the plan; F-015), `staff_task` waits for a person.
- A newer plan replaces an older `pending` or `offered` one (`replaced`); when an offered one is replaced, a "Our earlier offer is no longer valid; an updated offer follows shortly." draft step waits for the employee.

**Steps:** `POST /webhook/bahn/step` with `{step_id, outcome: done|failed|retry, operator, note, confirm_unclear?}`. Finishing an employee task (`proposal_id` task) wakes the workflow named in its note; finishing a plan's last open step wakes the agent (`agent_woken: true`).

**Simulated driver:** Claude Haiku 5.5 persona (replies appear in the Telegram demo group, F-015) on a FACTS block, checked by GLiDE (`contradicts`, p ≥ 0.5 gives a safe fact-only reply instead). With the order's `driver_unreachable` test flag (set in the last 20 min) it gives no answer.

**Errors:** each failure returns a reason: unknown or already-decided proposal, missing operator, bad action, missing `evidence_refs`, unusable option id, duplicate pending plan, missing buyer answer, message to anyone other than driver or pickup site (`sent:false`), GLiDE down (case not closed).

**Test switches (test-only):** on `/act` `simulate` = `ferry_sold_out`, `ferry_timeout_once`, `hotel_timeout`, `train_sold_out` or `flight_sold_out`; on `/step` `simulate: hotel_timeout`; on the event `simulate: driver_unreachable`. Test hooks with no agent: `POST /webhook/bahn/test/{propose_plan|check_journey|plan_driver_travel|escalate_urgent|message_driver|close_case|propose_action|plan_rebooking}`.

## Data (what is stored, schema or fields, retention, privacy/legal implications)
- Synthetic only: Bahn's fictional packet, simulated driver replies, `mock_generated` sailings, trains and flights, MOCK bookings (`MOCK-FERRY-...`, `MOCK-RECOVERY-...`). Nothing is booked for real.
- Snapshot time `2026-10-21T09:00:00Z`; all times UTC.

## Decisions and gotchas (why choices were made, rejected alternatives, known limits, traps)
- **User choices (2026-10-24):** Data Tables (no Docker/Postgres); Claude Haiku 5.5 agents, Claude Haiku 5.5 simulated driver (was GLM 5.3 Flash), GLiDE for routing and gates; codes + GLiDE classifier with root cause winning; late with no fix = new window + buyer draft; train and flight planning in scope; best ferry = on time, then price, then convenience; real timers and OR-Tools skipped.
- **Changes from the approved plan, told to the user:** the replacement-driver search lives inside `plan_driver_travel` (no separate workflow); the road verdict has three levels (`on_time` needs a 3 h buffer); the router answers at once and the control room polls; `propose_action` is no longer an agent tool; agent maxIterations is 20.
- **Ferry search (plan_rebooking):** dataset quotes plus generated sailings (±20% price, about 1 in 4 sold out), scored in code for terminal reach, check-in, hotel nights and the 3 h buffer. Why the 22:00 simulated sailing beats the 12:00 quote on CD-420299: one Helsinki hotel night instead of two.
- **Known limits:** positions and distances are straight lines x 1.25 between dataset cities (no map service); trains do not cross into Finland; hotel prices outside 4 dataset cities are a flat 110 EUR MOCK; the seeded context never changes, so the re-check cannot see new real-world events; thresholds (0.5 routing, 0.5 contradiction, 0.8 close, 45 min gap) are hand-picked.
- **Money:** expense amounts in the dataset are EUR or DKK with no rate given; the DKK rate is the fixed ERM II peg (about 7.46), marked `ponytail:` in propose_plan. Travel quotes are all EUR.
- **Auto re-plan after a failed booking (user choice, 2026-10-24):** the agent re-plans by itself; a person still approves the new plan. A failed hotel can also be retried by a person on its step, so do not both retry the hotel and approve a new hotel line.
- **Dataset facts that shaped tests:** no ferry is mid-crossing and all 4 hotels are before pickup at the snapshot, so those normal-gap rules are tested offline with a shifted clock; CD-420537's free drivers live in Hamburg, so its replacement is a local transfer with no train.
- **The LLM's wording can still slip** (e.g. "no costs approved" next to a EUR 450 total); the person sees the code-built plan lines and total.
- **n8n traps:** a second local n8n must not use port 5679 (task-runner broker); use 5688 / 5690. n8n-MCP 2.28.8 partial update fails against n8n 2.25.6, so edits go through the REST API as `setup.mjs` does. Data Table row delete needs `DELETE .../rows/delete?filter=...`. Buffer memory lives in the n8n process and is not cleared by `--reset-cases`.
